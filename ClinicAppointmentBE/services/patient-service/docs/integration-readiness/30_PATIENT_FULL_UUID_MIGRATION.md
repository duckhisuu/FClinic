# 30 — Full UUID vertical implementation

Patient API moves to `/api/v3/patients` for this breaking proposal; eight operations retained, v2 alias/coercion not supplied. `PatientWebConfiguration` protects v3 with the same authentication interceptor. `PatientInput` validates UUID strings without number/string coercion through `BusinessId`; canonical lowercase, v4 and RFC variant2 are mandatory. Body doctorId, optional appointmentId, nested recordId and appointment search filter are UUID. Numeric versions/page/size remain strict numbers.

Domain, ports, writer, policy, trusted Doctor mapping, search/response DTOs, repository JPQL bindings and all four JPA entities now use UUID business IDs. UUID comparisons use value equality. A newly created medical record receives random UUIDv4 before persistence; revision PKs use GenerationType.UUID. Patient generation remains random UUIDv4. Parent locks, optimistic version checks, no-op behavior, immutable references/authorship, atomic revisions and no network within write transaction remain intact.

Fresh target: `src/main/resources/db/schema/uuid/V001__patient_uuid_empty.sql`. This is a separate standalone bootstrap script, not Flyway baseline or an ALTER migration. Do not execute it alongside/after old V001. Four tables retain restrictive FKs, unique appointment reference, unique entity-version revision pairs, indexes, revision JSON and action/changeReason checks. Native uuid fields also enforce v4/variant by CHECK. Doctor/Appointment are external facts, not cross-database FK targets. Audit actor columns remain opaque strings. Versions remain bigint. Application remains `ddl-auto: validate`, SQL init never.

Fresh deployment now requires explicit `PATIENT_UUID_DB_URL`, `PATIENT_UUID_DB_USERNAME`, `PATIENT_UUID_DB_PASSWORD`; the old V2 env names are deliberately not a fallback to an existing mixed-ID DB. Tests bootstrap only owned disposable PG16.10 and then validate Hibernate mappings.

**LEGACY DATA MIGRATION REQUIRES OWNER MAPPING.** No in-place conversion, drop, backfill, hash/nameUUID mapping or deletion is implemented. A future migration must obtain authoritative old/new Patient, Doctor, Appointment, user, scope assignment/visit mappings; stage one-to-one mappings, detect missing/duplicate ownership, translate revision snapshots with provenance and validate relationships before separate owner-approved cutover. Old databases remain untouched.
